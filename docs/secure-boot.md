# Secure Boot support

`lbl` detects whether the platform has Secure Boot enabled and surfaces it two
ways:

- a warning row in the boot menu (`Secure Boot is ON - unsigned entries will be
  rejected`), and
- a `boot: Secure Boot is ON ...` line in the boot log
  (`\var\logs\leon\log.md`, `make qemu` / `scripts/run_qemu.sh`).

Detection reads the UEFI `SecureBoot` global variable and reports
Enabled/Disabled/Unknown; a missing or unreadable variable never blocks the
boot.

If Secure Boot is active and a boot entry's image is rejected by the firmware
at load time, `lbl` logs the reason
(`boot: <path> rejected by Secure Boot - sign it or enroll its key`) instead of
failing silently.

## Signing with your own keys

The host-side tooling is `scripts/sign.sh` (needs `openssl`, `sbsign` from
sbsigntools, and `python3`; the `.esl` writer is `scripts/gen-esl.py`, a
standalone replacement for efitools' `cert-to-efi-sig-list`).

```sh
# 1. Generate a personal PK/KEK/db key set into keys/ (git-ignored).
scripts/sign.sh setup

# 2. Stage and sign the ESP tree in place.
make stage
scripts/sign.sh sign-all        # or: make sign

# 3. Copy build/esp/* to your ESP and enroll the keys (below).
```

A single signature covers both the loader (`\EFI\BOOT\BOOT<ARCH>.EFI`) and the
kernel (`\EFI\leon\kernel.efi`). Re-run `make sign` after every rebuild.

Single-file signing also works: `scripts/sign.sh sign kernel.efi out.efi`.

## Enrolling keys

The firmware's Secure Boot configuration accepts the `.esl` files generated by
`scripts/sign.sh setup` (`keys/db.esl`, `keys/KEK.esl`, `keys/PK.esl`).

1. Disable Secure Boot in the firmware setup UI.
2. Enroll the keys **in order: db, then KEK, then PK** (matching most
   firmwares' "reset to setup mode then install" flow). Loading the db key
   moves the platform from Setup Mode to User Mode; PK last locks the policy.
3. Re-enable Secure Boot and verify it is active (the boot menu warning row is
   the quickest check; the firmware setup screen should also report it).

### Kernel/driver updates

An updated kernel (or loader) must be re-signed with the same db key, or the
firmware will reject it and the boot log will show the rejection message above.
Keep `keys/` (in particular `keys/db.key`) safe: losing it locks the machine
out of updating this boot path.

## Testing under QEMU

No key enrollment is needed to test: point `run_qemu.sh` at the OVMF/AAVMF
"snakeoil" Secure Boot firmware variables, whose key is the well-known
snakeoil cert (passphrase `snakeoil`). Sign the staged files **after**
`make stage`, then boot with `./scripts/run_qemu.sh` directly — not
`make qemu`, because that target re-runs `stage` and overwrites the signed
files with unsigned builds:

```sh
# x86:  /usr/share/OVMF/OVMF_CODE_4M.secboot.fd + OVMF_VARS_4M.snakeoil.fd
# arm64: /usr/share/AAVMF/AAVMF_CODE.secboot.fd + AAVMF_VARS.snakeoil.fd
# key:  /usr/share/ovmf/PkKek-1-snakeoil.key  (x86)
#       /usr/share/qemu-efi-aarch64/PkKek-1-snakeoil.key  (arm64)

make stage
printf 'snakeoil\n' | sbsign --key .../PkKek-1-snakeoil.key \
  --cert .../PkKek-1-snakeoil.pem --output build/esp/EFI/BOOT/BOOTX64.EFI \
  build/esp/EFI/BOOT/BOOTX64.EFI
printf 'snakeoil\n' | sbsign --key .../PkKek-1-snakeoil.key \
  --cert .../PkKek-1-snakeoil.pem --output build/esp/EFI/leon/kernel.efi \
  build/esp/EFI/leon/kernel.efi
OVMF_CODE=/usr/share/OVMF/OVMF_CODE_4M.secboot.fd \
OVMF_VARS=/usr/share/OVMF/OVMF_VARS_4M.snakeoil.fd \
./scripts/run_qemu.sh        # arm64: AAVMF paths + ARCH=arm64
```

With an unsigned loader, OVMF itself refuses to load it
(`Access Denied -- rejected probably by Secure Boot`) and falls through to
PXE. With the signed loader + unsigned kernel the boot log ends in
`boot failed: Error { status: ACCESS_DENIED }`; signing the kernel too boots to
the kernel handoff with the Secure Boot warning present.

Note: when booting a `make_esp.sh` image under OVMF on the `q35` machine,
attach it as SATA (`-drive file=build/leon-esp.img,format=raw,if=ide`) — OVMF's
default hard-disk boot entry targets the SATA controller, so a `virtio-blk-pci`
disk is never tried and the firmware falls through to PXE. On `virt` (arm64)
virtio-blk is the normal storage path.
